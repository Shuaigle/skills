# Spec and ticket storage

## Resolve the destination

An explicit user destination wins. Otherwise inspect the working repo's Git remotes. Use its GitHub origin; if origin is not GitHub, use the only distinct GitHub repo among the remaining remotes. Confirm the host and owner/repo with the available GitHub tools or authenticated `gh`. Support configured GitHub Enterprise hosts too. Do not infer the repo from a folder name or an unrelated CLI environment default. When several targets remain, ask which one.

A confirmed GitHub repo uses issues: keep the spec on the existing authorized issue for that feature, or create a spec issue when none exists; use one issue per output ticket. A repo without a GitHub remote uses `.scratch/<feature-slug>/spec.md` and `.scratch/<feature-slug>/<NN>-<slug>.md`; ensure `.scratch/` is gitignored. Show the resolved destination before writing. Drafts may use temporary files; do not maintain a second canonical copy.

Missing authentication, denied access, disabled issues, and API failures are errors, not evidence that the repo has no GitHub remote or no matching issue. Report the blocker; do not silently fall back to local files or create a duplicate. A source issue from a different repo does not change the destination: resolve that mismatch before writing.

Invoking `to-spec` authorizes its output once the destination meets the confirmation rules below. For `to-tickets`, the approved breakdown authorizes the output batch, including any source snapshot described below. Respect existing repo restrictions.

## Ownership and repeated runs

Generated specs start with `<!-- generated by to-spec -->`; generated tickets start with `<!-- generated by to-tickets -->`. The next line is `<!-- feature: <feature-slug> -->`. Tickets also carry `<!-- ticket: <NN>-<slug> -->`, independent of their GitHub issue number.

For `to-spec`, resolve an explicitly supplied issue first and verify that it belongs to this feature and authorized repository. Otherwise search open and closed issues in that repo. Read candidate bodies: a matching generated feature marker, a source link or clearly matching requirements can establish identity; a similar title alone cannot.

- An open issue explicitly named by the user, or the single unambiguous open match with a verified generated marker for the same feature, needs no extra destination confirmation.
- If the match depends on interpreting the issue content or a link rather than on one of those two signals, show the issue URL and why it matches. Wait for a yes before editing. If several candidates are plausible, ask which one.
- Before editing any closed issue, obtain explicit confirmation to update that exact issue while leaving it closed. An earlier confirmation that explicitly covered both the issue and its closed state counts; merely naming the issue does not.
- Create a new issue only after a successful search finds no match. Waiting for or being denied confirmation does not make a match disappear. Do not reopen an issue or create a duplicate to bypass confirmation. If a supplied issue conflicts with the feature or existing markers, stop for reconciliation.

Use these update boundaries:

- **Existing issue with a managed spec block:** replace only that block's payload for the matching feature. Preserve every byte outside it, including human text, comments embedded in the body, links and checkboxes.
- **Existing issue without a block or standalone spec marker:** append a managed block. Do not replace its body or change its title, labels, assignees, milestone, comments, checkboxes or open/closed state. This also applies to an existing task issue with a generated-ticket marker.
- **Legacy standalone generated spec:** when the first line is exactly `<!-- generated by to-spec -->` and the feature matches, keep the whole-spec format and update it in place. Do not silently wrap or migrate it, since old tickets may hash the whole body.
- **Local spec:** retain whole-file ownership rules; update only a matching standalone generated spec. An unmarked local file is a conflict, not an append target. For older marked local artifacts, the directory and numbered filename supply missing feature/ticket IDs.

A managed issue contains exactly one block, delimited by these exact lines:

```markdown
<!-- to-spec:begin -->
<!-- generated by to-spec -->
<!-- feature: <feature-slug> -->

<spec template content, ending with a newline>
<!-- to-spec:end -->
```

Missing, malformed, nested, duplicate or conflicting boundaries stop the run. Do not guess which text is owned, add another block, or publish elsewhere to escape a conflict. Reserve these boundary markers for the actual block, not examples inside issue text.

For `to-tickets`, reuse only unique matching generated output tickets. An unmarked output target is still a conflict; the spec append rule does not authorize overwriting human tickets. Exclude the canonical source artifact and every issue hosting a managed spec block from full-ticket reconciliation, even when it carries a generated-ticket marker and a different issue is the current source. If a host occupies a matching approved ticket target, stop for reconciliation rather than overwriting it or creating a duplicate. Report obsolete tickets instead of deleting or closing them automatically.

## Issue writes

Prefer the host's GitHub connector. Use authenticated `gh` when the connector cannot perform an operation. Discover the current tools; do not assume a specific MCP tool name exists. Keep issue bodies out of shell interpolation: use structured body arguments, or a temporary UTF-8 file with `gh issue create --body-file` / `gh issue edit --body-file`.

Before updating an issue, fetch its complete body and state again. Stop if the body changed since composing the update. If the issue closed after authorization, apply the closed-issue confirmation rule. Submit only the body; preserve title, comments, labels, assignees, milestone, state and unrelated fields. Use a conditional write when available. A pre-write reread alone cannot eliminate a concurrent edit between that read and the write; do not claim atomicity. Update only artifacts in the approved output.

Use the bundled helper after resolving an existing issue. Save the decoded API body as UTF-8 without newline conversion, not a CLI-formatted display or JSON string literal. It prepares a draft only and makes no network calls:

```bash
python3 <to-spec-dir>/scripts/spec_artifact.py compose-issue \
  --expected original-body.md --current reread-body.md \
  --spec spec-payload.md --feature <feature-slug> --output new-body.md
```

The output path must be new. The payload uses the spec template's generated/feature markers and ends with a newline. The helper rejects stale reads and malformed blocks; issue identity and authorization must be established before calling it. Send the resulting body through the connector, then read it back. Require the full saved body to match the draft byte for byte and the selected spec hash to match its intended value. Normalization for hashing is not permission to rewrite issue prose or relax this readback check. A mismatch is an uncertain result to reconcile, not a reason to overwrite again.

Before `to-tickets` replaces an existing issue body, run the same helper's ownership guard on the latest body. It rejects every managed-block host (not only the current source), malformed boundaries, and mismatched ticket identity:

```bash
python3 <to-spec-dir>/scripts/spec_artifact.py ticket-target --input reread-body.md \
  --feature <feature-slug> --ticket <NN>-<slug>
```

Respect existing issue conventions without creating labels, milestones or issue types just for this workflow. Never publish credentials, personal absolute paths or unrelated private details; use repo-relative paths and confirmed scope.

Create tickets in dependency order. Replace draft ticket numbers with the returned canonical issue URLs in each ticket's **Blocked by** field. Where supported, also create GitHub's native blocked-by relationships; use the returned issue ID where the API requires an ID, not an issue number. If native relationships are unavailable, retain the body links and report that limitation.

Read back every created or updated issue and verify its body and links before reporting success. After a timeout or partial failure, inspect the destination before retrying. Preserve confirmed URLs and resume the remaining work; do not duplicate a batch or roll it back by closing issues.

## Source identity and immutability

Every new ticket records:

- **Source spec:** the canonical host issue URL or repo-relative local spec path.
- **Source slice:** `to-spec-block-v1` for a managed issue block, otherwise `whole-artifact-v1`.
- **Source SHA-256:** the SHA-256 of the selected source as defined below.
- **Written against:** the code commit used to prepare it.

`to-spec-block-v1` selects the UTF-8 bytes after the opening boundary line's newline and before the start of the closing boundary line. This includes the generated/feature markers and the payload's final newline, but neither boundary nor surrounding issue prose. Require exactly one valid block with the same feature marker as the ticket. For hashing only, convert each CRLF pair in that payload to LF; do not trim or change any other bytes. This keeps the hash stable if an issue edit rewrites only line endings and unrelated prose, including checkboxes. Issue title, comments, labels and state are not hashed. A missing block, changed feature or changed payload after line-ending normalization stops a consumer for reconciliation.

`whole-artifact-v1` selects the entire issue body encoded as UTF-8, or the exact local file bytes. A ticket without `Source slice` retains this legacy whole-artifact meaning even if its source later gains a managed block. Never silently switch its hash interpretation; reconcile a mismatch through spec/ticket revision. Unknown slice values stop. Local sources use whole-file hashing, not issue-block extraction.

When reading a spec directly or generating new tickets from an issue, select its managed block when present; otherwise use the whole body. For local input select the whole file. Hash according to the selected format above. Record the slice and hash at the start, then reread the same source through the same interface and verify the same slice and hash at the end of ticket generation and before a consumer writes verification results. Outside-block issue text and comments are context, not silent amendments. A changed selected hash fails the run; an unrelated outside-block edit does not, and never authorizes rewriting that prose.

The helper reports the slice, feature and SHA-256. For a newly resolved issue, omit `--slice` to detect a valid block. For consumers, pass the recorded slice, or explicitly `whole-artifact-v1` when absent; for local files always pass `whole-artifact-v1`. For a managed slice also pass the ticket's feature:

```bash
python3 <to-spec-dir>/scripts/spec_artifact.py source --input source-body.md \
  --slice to-spec-block-v1 --feature <feature-slug>
```

To find a spec's tickets, search their `Source spec` locator and feature marker, including closed issues. Verify the returned bodies rather than relying on a ticket list in the spec. Exclude the source host itself from generated-output discovery.

Older local tickets may lack source metadata. Consumers may use an explicitly supplied or unambiguous adjacent `spec.md`, snapshot its current whole-file hash for the run, and retain the recorded commit drift check. Do not invent a historical hash or claim the old spec was verified. Ambiguous sources still stop; newly generated tickets must include all four fields.

When the input is local but the destination is GitHub, include a spec snapshot issue in the proposed batch so a fresh executor can read the source. After approval, publish the exact UTF-8 source body or reuse a unique issue with that same whole body. Read it back and require its bytes to match the local source. Tickets link that snapshot with `whole-artifact-v1` and its hash. The local source stays unchanged; an existing source issue is never rewritten to add a ticket list. If a required publication redaction would change the source, stop for spec revision.

Missing or inaccessible source artifacts stop the run. Report output URLs for issues and paths for local files. A host issue containing a managed spec remains the original work item, not disposable scaffolding; `to-docs` must not offer it for automatic or routine generated-artifact closure.
