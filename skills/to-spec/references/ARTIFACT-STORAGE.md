# Spec and ticket storage

## Resolve the destination

An explicit user destination wins. Otherwise inspect the working repo's Git remotes. Use its GitHub origin; if origin is not GitHub, use the only distinct GitHub repo among the remaining remotes. Confirm the host and owner/repo with the available GitHub tools or authenticated `gh`. Support configured GitHub Enterprise hosts too. Do not infer the repo from a folder name or an unrelated CLI environment default. When several targets remain, ask which one.

A confirmed GitHub repo uses issues: one spec issue and one issue per ticket. A repo without a GitHub remote uses `.scratch/<feature-slug>/spec.md` and `.scratch/<feature-slug>/<NN>-<slug>.md`; ensure `.scratch/` is gitignored. Show the resolved destination before writing. Drafts may use temporary files; do not maintain a second canonical copy.

Missing authentication, denied access, disabled issues, and API failures are errors, not evidence that the repo has no GitHub remote. Report the blocker; do not silently fall back to local files. A source issue from a different repo does not change the destination: resolve that mismatch before writing.

Invoking `to-spec` authorizes its output at the resolved destination. For `to-tickets`, the approved breakdown authorizes the output batch, including any source snapshot described below. Respect existing repo restrictions, but add no separate publication checkpoint.

## Ownership and repeated runs

Generated specs start with `<!-- generated by to-spec -->`; generated tickets start with `<!-- generated by to-tickets -->`. The next line is `<!-- feature: <feature-slug> -->`. Tickets also carry `<!-- ticket: <NN>-<slug> -->`, independent of their GitHub issue number.

Resolve an explicit artifact first; otherwise search open and closed issues in the selected repo, or the selected local directory, for that feature and verify the markers in its body. Reuse a unique matching generated artifact. Several matches require disambiguation. Do not overwrite an unmarked issue or file, or treat a similar title as ownership. For older marked local artifacts, the directory and numbered filename supply missing feature/ticket IDs.

Before updating an issue, fetch it again. Stop if its body changed since it was read; preserve comments, labels, assignees and unrelated fields. Update only the artifacts in the approved output. Report obsolete tickets instead of deleting or closing them automatically.

## Issue writes

Prefer the host's GitHub connector. Use authenticated `gh` when the connector cannot perform an operation. Discover the current tools; do not assume a specific MCP tool name exists. Keep issue bodies out of shell interpolation: use structured body arguments, or a temporary UTF-8 file with `gh issue create --body-file` / `gh issue edit --body-file`.

Respect existing issue conventions without creating labels, milestones or issue types just for this workflow. Never publish credentials, personal absolute paths or unrelated private details; use repo-relative paths and confirmed scope.

Create tickets in dependency order. Replace draft ticket numbers with the returned canonical issue URLs in each ticket's **Blocked by** field. Where supported, also create GitHub's native blocked-by relationships; use the returned issue ID where the API requires an ID, not an issue number. If native relationships are unavailable, retain the body links and report that limitation.

Read back every created or updated issue and verify its body and links before reporting success. After a timeout or partial failure, inspect the destination before retrying. Preserve confirmed URLs and resume the remaining work; do not duplicate a batch or roll it back by closing issues.

## Source identity and immutability

Every ticket records:

- **Source spec:** the canonical issue URL or repo-relative local spec path.
- **Source SHA-256:** the SHA-256 of the exact issue body encoded as UTF-8, or exact local file bytes.
- **Written against:** the code commit used to prepare it.

To find a spec's tickets, search their `Source spec` locator and feature marker, including closed issues. Verify the returned bodies rather than relying on a ticket list in the spec.

Do not trim or normalize the source before hashing. Re-read it through the same interface at the end of ticket generation; a changed hash fails the run. Issue titles, comments and state are not part of the spec body hash.

Older local tickets may lack source metadata. Consumers may use an explicitly supplied or unambiguous adjacent `spec.md`, snapshot its current hash for the run, and retain the recorded commit drift check. Do not invent a historical hash or claim the old spec was verified. Ambiguous sources still stop; newly generated tickets must include all three fields.

When the input is local but the destination is GitHub, include a spec snapshot issue in the proposed batch so a fresh executor can read the source. After approval, publish the exact UTF-8 source body or reuse a unique issue with that same body. Read it back and require its bytes to match the local source. Tickets link that snapshot and record its hash. The local source stays unchanged; an existing source issue is never rewritten to add a ticket list. If a required publication redaction would change the source, stop for spec revision.

For GitHub input, use the issue body as the spec; comments are context, not silent amendments to it. Missing or inaccessible source artifacts stop the run. Report output URLs for issues and paths for local files.
