# Prototype Logic

Answer one design question by letting the user drive a model. The artifact explores an idea; it does not prove production correctness.

## Frame the question

Use the current discussion and relevant code to name the question, starting state, actions, and assumptions. Use the project's domain vocabulary. Keep unresolved product choices visible as assumptions; do not treat a scenario you invented as the user's decision.

If the question is about appearance or layout, use a UI prototyping workflow instead. For a request spanning several models, choose one question that can be answered independently and state the scope.

## Build the artifact

Write one offline HTML file, with inline CSS and JavaScript, at `.scratch/<feature-slug>/prototype-logic.html`. Ensure `.scratch/` is gitignored. Keep state in memory; use no CDN, external requests, framework, bundler, server, database, or persistence.

Use `<!-- generated by prototype-logic -->` as the first line. Replace an existing artifact only when its first line matches that marker. Preserve any other file and choose an unused filename beside it; report the chosen path.

Separate a small domain module from the DOM: a reducer, state machine, pure functions, or a stateful module, whichever fits the question. The page calls its public interface; domain logic never reads the DOM and button handlers never mutate its internals. Keep the implementation small enough to inspect and extract.

The page contains:

- **Question and assumptions**, visible at the top, including any simulated time or network behavior.
- **Current state**, as labeled domain fields, updated after every action. Show the action's outcome or relevant error, including why an invalid action was rejected and whether state changed.
- **Free-play actions**, always available so illegal transitions can be explored. Use native, labeled buttons, keyboard access, and a readable status region.
- **Reset**, restoring the known starting state and clearing walkthrough progress and outcomes.
- **Guided scenarios**, covering the happy path, a tricky sequence, and an illegal action. Each starts from a known state and provides ordered action buttons with the expected domain outcome. Reset and replay must produce the same result; explicitly control time, randomness, and responses when they matter.

Keep styling readable. Spend effort on the question and observable state, not visual polish, abstractions, or a prototype test suite. Stub external effects; the artifact never performs real mutations or accesses production credentials.

## Verify and hand over

Open the HTML with available browser tooling before delivery. Check that it works offline, the buttons and status update, each guided scenario answers the original question, invalid actions produce the expected outcome, and reset followed by replay is deterministic. Inspect browser errors and basic keyboard operation. Repair failures within the prototype; if browser execution is unavailable, state which behavior remains unverified.

Give the user the file path, the question it explores, and any limitations of the model. Separate observed outcomes from assumptions still needing a decision. Do not claim the prototype validates production integrations or correctness beyond its scenarios.

When the user invokes `to-spec`, transfer the validated decisions and only the snippets that express them more precisely than prose. Do not invoke that user-only skill automatically. Building or evaluating the prototype does not authorize production edits, commits, branches, issues, database access, or deleting artifacts.
