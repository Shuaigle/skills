# To Tickets

Compile one spec into **tickets**: tracer-bullet vertical slices, each declaring the tickets that **block** it.

When speaking to the user, explain a tracer bullet as a narrow, working vertical slice through every affected layer, and a blocking edge as work that must finish first.

The spec owns the problem, scope, and decisions. Tickets own execution order and verification. Follow [artifact storage](../to-spec/references/ARTIFACT-STORAGE.md): a confirmed GitHub repo uses issues; a repo without one uses `.scratch/<feature-slug>/`. An explicit user destination takes precedence.

## Process

### 1. Read the source

Read exactly one spec, located from an issue URL, an issue number in the resolved GitHub repo, a local path, a feature slug or the current conversation. Fetch an issue's full current body. Missing, inaccessible or ambiguous, stop and name what is needed.

This skill is a compiler: spec bytes stay fixed; only marked output tickets are mutable. Resolve the destination and record the source locator and SHA-256 now. The same hash after ticket generation is part of this run's completion criterion.

### 2. Ground the breakdown

Explore only far enough to find seams, exemplars, runnable verification commands, and drift from the spec's recorded commit. Use vocabulary from the relevant vocabulary record and respect the area's ADRs.

Code or documentation that contradicts the spec ends the run: report the conflict and the spec revision it requires. Tickets may add paths, exemplars, commands, and ordering; a missing product, scope, implementation, or testing decision ends the run for spec revision.

### 3. Draft vertical slices

Break the work into **tracer bullet** tickets.

<vertical-slice-rules>

- Each slice cuts a narrow but COMPLETE path through only the layers required by the spec — vertical, NOT a horizontal slice of one layer
- A completed slice is demoable or verifiable on its own
- Each slice is sized to fit in a single fresh context window
- Put prefactoring first only when the source spec supports it and it addresses a concrete obstacle to delivering the slice

</vertical-slice-rules>

Give each ticket its **blocking edges** — the other tickets that must complete before it can start. A ticket with no blockers can start immediately.

**Wide refactors are the exception.** When one mechanical change, such as renaming a column or retyping a shared symbol, has a blast radius that prevents any vertical slice from landing green, load [WIDE-REFACTORS.md](references/WIDE-REFACTORS.md).

### 4. Quiz the user

Present the proposed breakdown as a numbered list. For each ticket, show:

- **Title**: short descriptive name
- **Blocked by**: which other tickets (if any) must complete first
- **What it delivers**: the end-to-end behaviour this ticket makes work

Name the destination repo or local directory. If a local source needs a GitHub snapshot issue, include that source publication in this proposed batch.

Ask the user:

- Does the granularity feel right? (too coarse / too fine)
- Are the blocking edges correct — does each ticket only depend on tickets that genuinely gate it?
- Should any tickets be merged or split further?

Iterate until the user approves the breakdown. This checkpoint edits the breakdown only; a requested change to the spec ends the run for spec revision.

### 5. Write the tickets

For GitHub, use one issue per ticket, created in dependency order (blockers first). Use the repo's title convention, or `<feature-slug>: <NN> — <title>`. Resolve each **Blocked by** entry to the returned issue URL. Add native dependencies where supported and report when only body links are available. If the source is local, publish or reuse its byte-identical spec snapshot issue as described in artifact storage, then link it from every ticket.

For local output, write one file per ticket under `.scratch/<feature-slug>/<NN>-<slug>.md`, numbered from `01` in dependency order. Each **Blocked by** entry names the local ticket path and title. Ensure `.scratch/` is gitignored. One ticket per issue or file, never a single combined artifact.

For repeated runs, reconcile only tickets whose first line is exactly `<!-- generated by to-tickets -->` and whose feature/ticket identity matches the approved output; older local files may derive that identity from their path. Preserve unmarked issues or files, the source spec and unrelated work; report what was preserved. An unmarked artifact occupying an approved target stops the run. Do not delete or close obsolete tickets automatically.

Each ticket must stand alone: the executing agent has not seen this conversation. Inline the conventions to follow, name an exemplar file where one helps, and stamp the commit the ticket was written against.

Read back the output, verify its source and blocker links, and require the original spec's content hash to match step 1. A mismatch fails the run. Never append a ticket list to the source spec. Return the confirmed issue URLs or local paths; on partial failure, report the completed subset and resume without duplicating it.

## Acceptance criteria

Every criterion carries a command and the output that means it passed. The executor ticks a box by running that command and matching its output, never by judgement, so a criterion written as prose leaves it nothing to run. Keep the commands safe to repeat: tests, builds, queries, read-only checks. The executor runs them more than once.

- [ ] Criterion — verify: `<command>` → <expected output>

Where you cannot write the command, first use an existing entry point and an observable result: an exit code, a matched string, a diff against a golden file. If that still leaves a verification gap, report it and stop for spec revision. New seams or architecture require a decision in the source spec; ticket generation cannot add them to make verification possible.

## STOP if

Conditions under which the executor stops and reports instead of improvising — e.g. the cited code no longer matches this ticket's assumptions.
