Implement the work described by the user in the spec or tickets. Accept local paths and GitHub issue URLs or numbers; resolve issue numbers against the confirmed repository. Read [ARTIFACT-STORAGE.md](../to-spec/references/ARTIFACT-STORAGE.md) for source resolution, hashes, ownership, and safe writes. Honor explicit source choices. If a required issue cannot be read, stop and report; do not create a local replacement.

When several tickets exist, work the **frontier**: read each referenced blocker and choose a ticket whose blockers have every acceptance box ticked. Issue closure alone does not prove acceptance passed. In a linear chain, work top to bottom.

## Rules

1. Read the current source bodies first, including the ticket's linked spec. For a generated ticket, resolve `Source spec` and compare the source's exact body/file bytes with `Source SHA-256`. Older local generated tickets lacking both fields may use an explicitly supplied or unambiguous adjacent `spec.md`; snapshot its current hash for this run without inventing a historical hash. Ambiguous sources, mismatched hashes, and missing provenance on issue or new-format tickets stop the run for reconciliation. Drift-check the spec/ticket's recorded commit against `HEAD`. If the code it cites has changed underneath it, stop and report — do not improvise around a stale plan.
2. Touch only what the spec/ticket puts in scope. No drive-by fixes; note them for a future ticket.
3. A ticket's STOP condition fires → stop and report.

In the stop report, explain the exact condition in plain language.

## Loop

Use the bundled `tdd` skill where possible, at pre-agreed seams.

Run typechecking regularly, single test files regularly, and the full test suite once at the end.

Done = every acceptance criterion verified by running its command, not by judgement. Tick a criterion's checkbox once its command has run and the output matched. A check that failed, or that you never ran, stays `[ ]`.

Tick only tickets whose body starts exactly with `<!-- generated by to-tickets -->`, whether a local file or an issue. Anything else is someone's own writing: run its checks and report the results without editing it. Before writing, reread the ticket and linked spec, confirm the source hash and verification text still match what you ran, and change only the verified checkboxes using the shared safe-write rules. Preserve other edits; if the relevant text changed, stop and report instead of overwriting it. Never edit the spec or close issues.

The next run reads those boxes to tell which blockers have landed, and `to-docs` reads them to tell whether the work is finished. A box you tick without running its command misleads both.

## Finish

Commit to the current branch only when the user or the repo's policy has authorized commits; otherwise stop after verification and report the diff.

Then stop and point the user at the next two steps:

1. `review`, run from a session that did not write this code, preferably on another model.
2. `to-docs`, once the review's fixes land. The spec's decisions are the only part of this run that has nowhere to live; that skill decides what survives.
